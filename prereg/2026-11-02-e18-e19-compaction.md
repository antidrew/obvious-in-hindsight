# E18 / E19: the compaction amnesia (prereg 2026-11-02, before any run)

## Observation
Harness: events compaction with `token_threshold 14336, event_retention_size 5` (starter + README; the same values in our
runner). ADK's `LlmEventSummarizer._format_events_for_prompt` keeps only `part.text` (forum 754783; read in
`google/adk/apps/llm_event_summarizer.py:73-80`), so tool calls and tool results never reach the summariser.
Audit (`scripts/compaction_audit.py`, per-call logs, rb-style training pool, agents e2b + e10):
- Compaction fires in 82-84% of attempts (mean 1.24-1.64 per attempt), first at model call ~12 (median; p25 9, p75 15).
- After it, the request holds the system prompt, a model-written summary and the last 5 events. No tool result older than that.
- The verbatim issue is gone: the mean share of long issue lines still present is 6%; all gone in 78% (n = 37, e10).
- 90% of post-compaction file reads re-read a file already read (1782/1985 e2b, 157/174 e10), 3.1-4.2 calls per attempt
  (11-15% of a 28-call budget).
- No prompt in the project has included `{problem_description}` in the root instruction.

## Hypothesis
Compaction at ~call 12, near the first edit, causes three things we recorded as separate findings:
(a) the wrong-contract patches (exact strings lost with the issue; failures.md section 2), (b) incomplete multi-site fixes
(sites read earlier are forgotten; C20), and (c) the plateau above 28 calls (extra calls go to re-reading, C3).

## Assumptions
1. The hidden-set scorer runs the same compaction (README 7.2, starter cell 10). 2. AgentTool sub-agents run without compaction
(`agent_tool.py` builds a Runner with no App config; harness.md). 3. Overflow in a sub-agent returns to the root as a tool
error (`agent_runner.py:269`), so it is recoverable. 4. Context without compaction stays below ~26.6k tokens for most
attempts (`prompt + max_output_tokens <= 32768`, probed on the server). Estimated from logs: median 22k, 34% over 26k,
an over-estimate because re-reads disappear. 5. A longer prompt per call does not cost more than the summariser and re-reads save.

## Arms (one change each, base = agent_idris24, the Kaggle file)
- **agent_idris24**: control.
- **agent_e18**: control + a verbatim `{problem_description}` section at the end of the system prompt. Tests (a) alone.
- **agent_e19**: the same agent as an AgentTool `solver` under a thin dispatcher, so no compaction at all; max_output_tokens 6144
  (overflow at 26.6k); verbatim issue in the instruction; an environment section (the solver does not see the harness's first
  message or file listing). Tests (a) + (b) + (c). Overflow or a text-only stop returns to the dispatcher, which restarts
  the solver with "Resume" (fresh context, the tree persists).

## Decision rule
Adopt an arm at pooled (rb64 + OOD-45) ≥ +2.0 per pass, one-sided permutation p ≤ 0.15, OOD ≥ −1, and output tokens/task
≤ +10% (Kaggle time). Reject at pooled ≤ 0. Otherwise two more passes. A gain needs its mechanism counter (compactions and
re-reads for e19; verbatim strings kept for e18) or it is "plausible", not "shown".
If e19 wins, Kaggle runtime prediction before upload: tokens/task and calls/task against idris24 (finished at 0.17).

## What would falsify the theory
e19 removes compaction and re-reads (mechanism holds) and the solve rate does not move: then amnesia is not what limits solves
and we return to model capability. If e19 overflows in > 30% of attempts, assumption 4 broke; next step is token thrift, not a verdict.

## Addendum (2026-11-02, written before any E18/E19 full-run result; only the 9-task e19 mechanics smoke had been read)
Forum 747857 calibrated Kaggle at 900.8 s per million reported tokens (prompt + completion, repeated context counted), so longer
prompts cost Kaggle time, and output tokens alone do not predict it. e19's prompts are longer by design. The time gate in the
decision rule is therefore: projected Kaggle hours from `scripts/kaggle_time.py` (per-call logs) ≤ 11.0 h and ≤ the control's
+10%, replacing "output tokens/task ≤ +10%". If e19 passes on solves and fails on time, it is not rejected: the next arm
trades time back (lower max_tool_calls, smaller tool results), since re-read calls are gone.
